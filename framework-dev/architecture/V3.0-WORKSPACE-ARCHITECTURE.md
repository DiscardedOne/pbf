# Project Blueprint Framework v3.0.0 — Workspace Architecture Specification

## Document purpose

This specification defines the accepted PBF v3.0.0 source and workspace architecture, ownership model, configuration, agent-operating contract, CLI behavior, integrity manifest, path resolution, workspace lifecycle, quality model and compatibility boundaries. It remains the normative reference for the stable framework.

## Status and decision authority

- **Status:** Accepted stable architecture, revision 1.3.4.
- **Framework version:** 3.0.0, sourced from the root `VERSION` file.
- **Workspace architecture revision:** 1.3.4; this revision is preserved by the distribution and maintenance work.
- **Primary use:** A reusable, adaptive documentation-planning framework for a human owner working with an AI agent.
- **Decision authority:** The owner supplies project context, priorities, decisions and approvals. The agent performs discovery, research, analysis, documentation and validation within its actual capabilities and authorized permissions. PBF supplies the methodology, instructions, templates, state model and tooling.
- **Release boundary:** The developer repository produces one product artifact, the Agent-First Release ZIP.
- **Approval rule:** Acceptance of this architecture authorizes work within the stated framework scope. It does not authorize unrelated application development, deployment, external publication or destructive changes outside the selected source workspace.

This document records architectural decisions. The implementation, tests, templates and release documentation must remain consistent with it. If implementation evidence reveals a material contradiction, record the issue and obtain an explicit decision before changing the architecture.

# 1. Executive summary

PBF v3.0.0 creates a documentation-focused workspace with three principal areas:

1. `docs/` — project-specific documentation and supporting artifacts.
2. `_framework/` — reusable framework runtime, rules, templates, defaults and reference material.
3. `_control/` — project-specific configuration, state, registers, approvals and continuity records.

The workspace root contains three deliberate entry points: `README.md` for the human owner, `AGENTS.md` for an agent operating the workspace, and `bp.py` as the stable command launcher. Project-specific agent rules live in `_control/PROJECT-RULES.md`, separately from framework-managed instructions. PBF does not assume that every agent harness automatically discovers `AGENTS.md`; the agent must use an actually supported discovery or explicit instruction-loading mechanism.

The developer repository and generated workspace are separate products. The developer repository contains the full maintained source, tests, architecture and release tooling. A release build generates a project-neutral workspace starter, assembles a minimal bootstrap runtime and packages the user-facing Agent-First Release ZIP. The nested package contains only the operating instructions, bootstrap runtime, helper and workspace starter required by the Agent-First setup flow.

The root `VERSION` is the single authoritative framework-version input. The source build generates the framework integrity manifest; workspace creation verifies and consumes the existing starter package without regenerating that manifest. `SourcePaths` and `WorkspacePaths` remain separate, and workspace creation does not initialize Git or bulk-scaffold the full potential document catalog.

The framework is designed to be agent-harness-neutral. This is an architectural goal, not a claim that every harness has the required file access, terminal capability, persistence or instruction-following behavior. Those capabilities must be established in the actual environment.

PBF intentionally provides no v2.x workspace migration, general workspace upgrade, workspace refresh mechanism, automatic software installation or OS-level sandbox. The owner explicitly confirms the proposed workspace destination before setup and separately confirms before P0 discovery begins.

# 2. Goals and non-goals

## 2.1 Goals

The v3.0.0 architecture must:

1. Separate reusable framework logic from project-specific documentation and persistent project state.
2. Make a project workspace's root identity belong to the project, not to the framework.
3. Keep application source code outside the documentation workspace.
4. Provide one stable, cross-platform CLI launcher.
5. Make workspace creation repeatable, safe and independently verifiable.
6. Centralize physical path resolution and remove old-layout hardcoding.
7. Preserve document IDs, document-relative paths, approval fingerprint semantics and the v2.3.3 golden fingerprint for an unchanged fixture.
8. Keep framework version ownership singular and workspace schema/layout versioning separate.
9. Detect accidental modifications to framework-managed files without pretending that an in-workspace hash manifest is a security boundary.
10. Provide a compact, portable, agent-neutral instruction contract.
11. Keep project-specific agent preferences outside framework-managed instructions.
12. Support iterative, adaptive documentation rather than bulk generation of empty catalog documents.
13. Make it possible to evaluate genuine project discovery and multi-session continuity early in the release process.
14. Support Windows and POSIX-style environments using standard-library Python only.
15. Keep framework developer tooling and history out of generated project workspaces.

## 2.2 Non-goals

The v3.0.0 scope does not include:

- Application source-code creation, hosting or deployment.
- Replacing the agentic harness, model, tools or user interface.
- Requiring any named AI harness.
- Maintaining the v2.3.3 project-workspace layout.
- Migrating existing v2.3.3 project documents or approvals.
- Refreshing or upgrading an existing workspace as a general update mechanism.
- Automatically merging customized framework files during framework upgrades.
- A general-purpose plugin marketplace or dynamic plugin loader.
- Project-specific template overrides in the initial release.
- Automatic semantic proof that requirements, traceability links or architecture are correct.
- A CI workflow or manual execution of a full CI-equivalent platform/version matrix.
- Full Mermaid rendering as a required runtime function.
- Treating the framework integrity manifest as tamper-proof security enforcement.

## 2.3 Design principle

The framework must separate **reusable rules**, **project knowledge**, and **project deliverables**. Each fact must have one authoritative home. Other files should link to it or derive it rather than maintain competing copies.

## 3. Core architecture decisions

The following decisions are normative for v3.0.0 unless changed through an explicit architecture revision. Each decision appears once; detailed implementation contracts are defined in the sections cited by topic below.

| ID | Decision | Rationale |
|---|---|---|
| DEC-001 | Make a clean break from the v2.3.3 workspace layout; no legacy layout support or migration utility. | No production project workspaces exist to preserve, so dual-layout behavior adds cost without user value. |
| DEC-002 | Use `docs/`, `_framework/` and `_control/` as the three principal workspace areas. | Separates project deliverables, reusable framework machinery and project-specific state. |
| DEC-003 | Use root `README.md`, `AGENTS.md` and `bp.py` as the human, agent and command entry points. | Gives each audience one clear starting point. |
| DEC-004 | Keep `AGENTS.md` framework-managed, verbatim and project-neutral; place project-specific agent rules in `_control/PROJECT-RULES.md`. | Prevents framework updates from overwriting project rules. |
| DEC-005 | Keep `AGENTS.md` at or below 14,000 Unicode characters, targeting 12,000 or less. | Provides room below known context-file truncation thresholds without assuming a universal harness limit. |
| DEC-006 | Make the framework agent-harness-neutral; describe host-specific context discovery only through optional, evidence-backed adapters. | The framework must not depend on a specific agent harness or any other named harness. |
| DEC-007 | Use one thin, context-aware `bp.py` launcher in source and workspace distributions. | Preserves a stable command interface without duplicating business logic. |
| DEC-008 | Keep source-only `verify`, `build` and `new` implementations out of generated workspaces. | Separates framework maintenance and package creation from project operation. |
| DEC-009 | Generate `_framework/FRAMEWORK-MANIFEST.json` at build time; `new` verifies but never regenerates it. | All workspaces created from one artifact share the same integrity baseline. |
| DEC-010 | Source-root `VERSION` is the sole release version input; the installed framework manifest owns the installed version. | Eliminates duplicate framework-version authority. |
| DEC-011 | `_control/WORKSPACE.json` owns workspace schema/layout versions and permitted project choices only; it contains no framework version or arbitrary path map. | Keeps workspace configuration small and prevents path escape through configuration. |
| DEC-012 | Put static machine-readable defaults in `_framework/defaults/workspace-defaults.json` and visible policy prose in `_framework/defaults/workspace-policy-defaults.md`. | Retains v2.3.3 defaults while making framework policy visible and hash-tracked. |
| DEC-013 | Resolve every workspace path through one immutable `WorkspacePaths` object selected by `layout_version`; keep source paths in a separate `SourcePaths`. | Removes hidden path coupling and keeps source/workspace concerns separate. |
| DEC-014 | Use `framework-dev/SOURCE-MANIFEST.json`, `_control/WORKSPACE.json` and `starter/_control/WORKSPACE.json.template` as distinct source, live-workspace and seed markers. | Prevents source/starter marker collisions. |
| DEC-015 | Use `docs/04-architecture/adr/` as the single canonical ADR path. | Aligns runtime behavior with the existing catalog and document paths. |
| DEC-016 | Preserve document IDs, paths relative to `docs/`, approval fingerprint inputs and the v2.3.3 golden fingerprint. | A physical workspace-layout change must not silently change document identity or approval semantics. |
| DEC-017 | Normalize managed text hashes to LF and ship `.gitattributes` with explicit LF rules. | Prevents Git line-ending conversion from appearing as framework drift. |
| DEC-018 | Write every generated text file as UTF-8 without BOM and LF. | Makes workspace generation deterministic across Windows and POSIX environments. |
| DEC-019 | Keep `.gitignore`, `.gitattributes`, `PHASES.md`, `WORKSPACE.json` and `PROJECT-RULES.md` as project-owned seeds/configuration. | These are initialized from defaults but belong to the project after creation. |
| DEC-020 | Do not bulk-scaffold catalog documents during `new`. | Discovery and accepted D0.02 determine the appropriate project document set. |
| DEC-021 | Use disposable, owner-controlled workspaces for methodology evaluation; do not embed evaluation-project material as permanent product examples. | Tests the framework without embedding evaluation-project documentation in the product. |
| DEC-022 | Do not build a general workspace refresh, upgrade or migration command. | Disposable test workspaces can be discarded and recreated from the accepted starter package. |
| DEC-023 | Defer `TRACE001` until real requirement-entry structures are observed; if later justified, begin warning-only. | Avoids speculative parsing and false-positive approval failures. |
| DEC-024 | Defer CI and a full manual Python/OS matrix; `verify` reports only the environment actually used. | Keeps v3.0.0 focused while preserving truthful release evidence. |
| DEC-025 | Defer project template overrides. | No current product requirement justifies the resolution and maintenance surface yet. |
| DEC-026 | Require Python 3.11 or newer; treat 3.11–3.15 as a compatibility target, not a tested matrix claim. | Avoids end-of-life interpreters while keeping compatibility claims evidence-based. |
| DEC-027 | Make the thin launcher parseable by Python 3.8 grammar so it can report the Python 3.11 minimum before importing newer-syntax modules. | Unsupported runtimes receive an actionable message instead of a syntax error. |
| DEC-028 | Detect case-folded and Unicode-normalization path collisions before packaging and workspace creation. | Prevents Linux-valid archives from colliding on case-insensitive filesystems. |
| DEC-029 | Make `new` refuse source-tree destinations and existing final destinations, stage as a sibling, validate fully, recheck the final destination immediately before a same-filesystem rename, and clean up its own staging area on failure. | Prevents source pollution and partial workspaces; a small cross-process race remains because portable standard-library Python has no POSIX atomic no-replace directory rename. |
| DEC-030 | `new` never runs `git init`; it prints optional Git setup instructions. | Repository creation is an explicit owner decision. |
| DEC-031 | Validate Windows-safe project names, derived slugs and destination path length on every host. | Avoids platform-specific creation failures. |
| DEC-032 | Define required files/structural roots separately from optional empty directories; runtime creates optional directories on demand. | Git and ZIP archives do not reliably preserve empty directories. |
| DEC-033 | Retain `_control/logs/overrides/` for policy-override records; do not create a template-override directory. | Avoids conflating policy exceptions with deferred template customization. |
| DEC-034 | Build the starter once per test session, copy it into temporary fixtures and use `new` in focused end-to-end tests. | Keeps regression tests efficient while exercising the public creation path. |
| DEC-035 | Make core tests network-independent and temporary-directory-based. | Improves repeatability and avoids dependence on user data. |
| DEC-036 | `verify` prints the actual interpreter, Python version, OS/platform, architecture and test summary when run. | Release notes can state what was genuinely executed without a separate CI record-export feature. |
| DEC-037 | Complete mechanical path/command corrections before release; complete narrative documentation after validation. | Alpha users must not receive stale instructions, while narrative refinement should use evaluation evidence. |
| DEC-038 | Disposition every v2.3.3 archive file exactly once in the source build plan; keep framework-dev content out of project workspaces. | Prevents missing files and ownership confusion during the clean break. |
| DEC-039 | Test source/workspace mode separation, starter marker handling, the compatibility fingerprint golden, path safety and fresh-package extraction before release. | Makes the central architecture and compatibility claims verifiable. |

Detailed requirements and tests in later sections refine these decisions; they do not introduce a second source of truth for them.

# 4. Canonical directory layouts

## 4.1 Framework source repository

The developer repository is the authoritative maintenance and release-production input. Its functional areas are separated so runtime, tests, authored release assets and generated outputs do not become mixed. The layout may evolve without changing the generated workspace architecture.

```text
Project-Blueprint-Framework/
├── README.md
├── DEVELOPMENT.md
├── CONTRIBUTING.md
├── VERSION
├── bp.py
├── .gitignore
├── .gitattributes
├── _framework/
├── starter/
├── src/blueprint_framework/
├── framework-dev/
│   ├── SOURCE-MANIFEST.json
│   ├── architecture/V3.0-WORKSPACE-ARCHITECTURE.md
│   ├── tests/
│   ├── CHANGELOG.md
│   └── RELEASE-CHECKLIST.md
├── release-assets/
│   ├── README-RELEASE.md
│   ├── QUICKSTART.md
│   ├── docs/
│   └── agent/
├── tools/
│   ├── agent-bootstrap/
│   └── release/
└── dist/                         # Generated; ignored by Git
```

`_framework/` contains the runtime copied into a generated workspace. `starter/` contains project-neutral workspace seeds. `src/blueprint_framework/` contains source-only CLI, build and package operations. `framework-dev/` contains normative developer references and maintained tests. `release-assets/` contains authored inputs copied into the user-facing release. `tools/agent-bootstrap/` contains the separately tested bootstrap helper, while `tools/release/` contains the complete release compiler. `dist/` is generated output and is not source of truth.

### Source-only files

- `VERSION` is the single framework release-version input.
- `framework-dev/SOURCE-MANIFEST.json` identifies the source tree.
- `src/blueprint_framework/` contains source-only commands and build/package implementation; these modules are not copied into generated project workspaces.
- `framework-dev/`, `release-assets/` and `tools/` are developer/release assets and are not copied into generated project workspaces.
- `dist/` contains generated artifacts only and must remain Git-ignored.

### Source command implementation and package contract

The root `bp.py` launcher selects source or workspace mode. Source-only commands are implemented under `src/blueprint_framework/`; workspace commands are implemented under `_framework/tools/`. `bp.py verify --scope bootstrap` validates only the inputs required for workspace creation. `bp.py verify` validates the maintained developer repository. `bp.py verify --tests` additionally executes the maintained test suite. `bp.py build` validates the maintained source, runs tests by default, builds the workspace starter and verifies the exact generated archive.

### Starter marker rule

The starter contains `WORKSPACE.json.template`, never a live `_control/WORKSPACE.json`. The source marker remains at `framework-dev/SOURCE-MANIFEST.json`; it identifies the source repository and is not copied into a generated workspace.

Git does not preserve empty directories; the build must not rely on empty ZIP directory entries. Runtime commands create optional directories when needed. `.gitkeep` is not required unless a specific source-only need is documented. Required files, not empty folder existence, define a valid workspace.

# 6. Agent-harness-neutral operating contract

## 6.1 Framework neutrality

The framework must not depend on one named AI agent, model provider, editor, plugin system, proprietary tool API or context-loading mechanism.

The core framework operates on files and, where available, a shell/command execution capability. It must remain usable by different agentic harnesses that can:

- Read project files.
- Write project files with user-authorized access.
- Maintain a working directory rooted at the project workspace.
- Optionally execute the Python CLI for structural validation and mutations.
- Present questions and proposed changes to the owner.

A shell is required for automated helper execution, but not for understanding the documents or following the manual workflow. If the host does not provide shell execution, the agent must state which automated checks it cannot run and use documented manual checks where practical.

The framework must not contain assumptions about a particular agent's memory system, connector names, UI, model naming, prompt syntax, internal APIs or tool-call format.

## 6.2 `AGENTS.md` as the canonical portable entry point

`AGENTS.md` is the canonical workspace instruction file. It is selected because it is a widely used convention and is verified for the intended initial agent environment. It is **not** assumed that every harness automatically loads it.

Each integration must use one of two mechanisms:

1. The harness automatically discovers and loads `AGENTS.md` from the workspace root; or
2. The user/host explicitly bootstraps the agent with `AGENTS.md` as the required project context.

The generated README must include a copy-paste initial prompt that points the agent to `AGENTS.md` for harnesses without automatic discovery.

The framework must describe the distinction between the canonical instruction file and the host's actual context-loading behavior. It must never claim that instructions were loaded unless the host or a verification procedure provides evidence.

## 6.3 `AGENTS.md` size budget

- Hard maximum: **14,000 Unicode characters**.
- Target maximum during editing: **12,000 Unicode characters**.
- The test measures decoded Unicode character count, not UTF-8 byte length.
- The file must not be silently truncated to fit. `verify` and `build` fail if the hard limit is exceeded.
- Detailed procedures, examples, full command syntax and specialist checklists belong in on-demand `_framework/` references; project-specific constraints belong in `_control/PROJECT-RULES.md`.
- `AGENTS.md` is copied verbatim from the framework starter. Project name, profile and project identity must never be substituted into it.

v3.0.0 must keep the mandatory contract concise, with 12,000 characters as the editing target and 14,000 as a hard upper bound. The budget is a framework safety margin, not a promise that every harness has the same context-file limit. Some hosts impose a configured limit; others calculate a dynamic limit from model context size. Hosts may truncate, progressively discover, merge or security-scan instructions differently. The selected host's actual cap and loading behavior must be checked during validation; if its effective cap is lower than the file's length, the integration test fails until the file or host configuration is corrected.

### Mandatory content in `AGENTS.md`

The root file must cover, within the size budget:

- Role and intended outcome.
- Startup and workspace discovery.
- How to confirm the file has been loaded or explicitly bootstrapped.
- Required first reads: project rules, STATE and index/real handoff as applicable.
- The filesystem as durable source of truth, not conversation memory.
- Progressive elaboration and adaptive document architecture.
- Source-of-truth and stable-ID rules.
- Distinguishing facts, inferences, assumptions and owner decisions.
- High-value conversational discovery rather than a large intake questionnaire.
- Approval, revision and authorization boundaries.
- Checkpoint and session-close requirements.
- Validation commands and truthful reporting.
- No unauthorized destructive or external actions.
- On-demand reference map.
- Owner shortcut phrase table, including status/next/checkpoint/gate/audit/park/revisit/replan/explain/wrap up.
- A concise state line at the end of every substantive agent message, derived from persisted workspace state.

The agent file must not include project-specific identity substitutions. Project name and profile are read from `WORKSPACE.json` and project records.

## 6.4 Project-specific agent rules

`_control/PROJECT-RULES.md` is project-owned. It may contain:

- Project-specific constraints.
- Terminology preferences.
- Domain-specific interpretation rules.
- Owner-approved working preferences.
- Restrictions on data handling or research.
- Additional review and communication expectations.
- Explicit project-specific agent permissions and limits.

`AGENTS.md` must tell the agent to read this file. The file is never replaced by framework updates. Empty/default rules are allowed at workspace creation; the agent should not invent project rules.

## 6.5 Optional harness integration and instruction discovery

The canonical portable instruction file is root `AGENTS.md`. The framework does not assume a host loads it automatically, nor does it assume universal names, search scopes, context limits or precedence for additional instruction files. A compatible agent must explicitly read `AGENTS.md` and `_control/PROJECT-RULES.md` when automatic loading has not been independently established.

Harness-specific discovery, security scanning, context truncation and tool-permission behavior are external capabilities. They may be described in a separate, version-specific integration record when such validation is actually performed. They must not become required framework runtime dependencies or change workspace paths, document semantics, approvals or core framework behavior.

A scanner result is an observation about the scanned scope and implementation, not proof that instructions were loaded or that an environment is sandboxed. Do not disable a host security control to obtain a passing result. Unknown or unavailable capabilities must be reported as such.

## 6.6 Portable agent setup contract

A capable agent must establish, in the actual environment that will access the workspace, that it can read and write files, execute Python 3.11 or newer, and access a persistent destination authorized by the owner. If any required capability is missing, it must stop and explain the limitation; an instruction package cannot grant filesystem or terminal permissions.

The agent proposes a project name and exact destination, inspects the parent directory, checks for conflicts and obtains explicit owner approval before creation. It must not overwrite, merge or delete an existing workspace. It uses the supplied bootstrap helper to verify the curated runtime and delegates creation to the existing `bp.py new` command. After creation it validates the workspace, reads the generated `AGENTS.md` and `_control/PROJECT-RULES.md`, records minimal setup provenance in an existing initial project-control record, and cleans up only temporary files it created.

Setup completion and P0 discovery are separate stages. The agent reports the exact destination, verification results and limitations, then asks whether the owner is ready to begin P0. P0 begins only after the owner explicitly confirms. The bootstrap process does not initialize Git, install software, make network calls or establish an OS-level sandbox.

# 7. Workspace configuration and version ownership

## 7.1 `WORKSPACE.json`

The live marker is `_control/WORKSPACE.json`. It owns:

- `workspace_schema_version`.
- `layout_version`.
- Project identity and display name.
- Selected project profile.
- Explicitly project-variable choices that are part of the workspace schema.
- Optional agent-integration metadata.

It does **not** own `framework_version`, arbitrary physical path mappings, framework hashes, static profile definitions, catalog defaults, template paths, bootstrap document IDs, reserved vision/architecture IDs, index-document lists or duplicated framework policy prose.

All physical paths are derived by `WorkspacePaths` from the supported `layout_version`. No `paths` object is permitted in schema v1.

### Illustrative schema

```json
{
  "workspace_schema_version": 1,
  "layout_version": 1,
  "project": {
    "name": "Example Project"
  },
  "profile": "standard",
  "agent_integration": {
    "profile": "generic",
    "additional_instruction_files": []
  }
}
```

The final JSON Schema must define required/optional properties, types, allowed values, unknown-key behavior and validation errors. The `project.name` is display metadata, not a filesystem path.

### Framework-owned defaults

Static configuration removed from the v2.3.3 `WORKSPACE.json` must remain visible and hash-tracked under `_framework/defaults/`:

- `_framework/defaults/workspace-defaults.json` contains machine-readable defaults and fixed definitions: profile names/ranks and structured profile descriptions, bootstrap document IDs, reserved vision and adaptive-architecture IDs, default index-document list, fixed catalog/template references, phase/gate defaults, semantic-source roles, required/optional directory definitions, supported asset categories and standard register identifiers.
- `_framework/defaults/workspace-policy-defaults.md` contains human-readable default policy text formerly embedded in the workspace configuration, including the structural-impact policy and explanations of profile behavior and other policy prose that owners/agents must be able to review. The machine-readable `profile_policy` descriptions remain in the JSON defaults.
- `_framework/WORKSPACE-CONFIG.md` explains how these defaults are interpreted, which values the project may select, and what is not user-configurable.

The machine-readable defaults file also owns the semantic-source role map, required-versus-optional directory definitions, supported asset categories and fixed catalog/index behavior. Both files under `_framework/defaults/` are included in `FRAMEWORK-MANIFEST.json`. They are framework-owned defaults, not copies of project-specific choices. `WORKSPACE.json` stores the selected profile and permitted project-level settings only. A project may record a justified local policy in `_control/PROJECT-RULES.md` or an appropriate register; it must not edit framework defaults as a shortcut.

`workspace-defaults.json` must include its own `defaults_schema_version` and a documented key inventory. The installed `_framework/FRAMEWORK-MANIFEST.json` declares the supported defaults schema version or range. `build` validates the defaults file against its schema and tests that the complete v2.3.3 non-path configuration inventory has a disposition. Project workspaces may select a profile but cannot replace the framework-owned profile-rank table, bootstrap document IDs, reserved IDs, index-document defaults or phase/gate definitions through `WORKSPACE.json`.

The implementation must inventory all non-path settings currently found in v2.3.3 `registry/WORKSPACE.json` and classify each into one of: framework default, project-selected value, generated state or obsolete setting. No setting may disappear without an explicit disposition.

## 7.2 `FRAMEWORK-MANIFEST.json`

The installed marker is:

`_framework/FRAMEWORK-MANIFEST.json`

It owns the installed framework version and the integrity baseline for framework-managed files.

### Version ownership lifecycle

1. Source-root `VERSION` is the release input during development/build.
2. `build` reads `VERSION` and writes the value into the built framework manifest.
3. `new` verifies the manifest and copies it unchanged into the workspace.
4. Workspace commands report the installed `framework_version` from the manifest.
5. `WORKSPACE.json` never stores another framework version.

The version parser must accept stable semantic versions and alpha identifiers, including `3.0.0-alpha.1`. Build and release tests must confirm prerelease parsing and ordering behavior.

## 7.3 Manifest schema and contents

The manifest should record at least:

- `manifest_schema_version`.
- `framework_version`.
- `workspace_schema_versions_supported` or an equivalent compatibility declaration.
- `layout_versions_supported`.
- `hash_algorithm` (SHA-256 for v3.0.0).
- `text_hash_policy`.
- A sorted list/map of framework-managed relative file paths and their hashes.

It must not include itself in the file hash list. File paths are workspace-root-relative POSIX paths.

### Managed file set

The build owns the authoritative allowlist. At minimum it includes:

- Root `AGENTS.md`.
- Root `bp.py`.
- All runtime/reference/template files under `_framework/`, except the manifest itself.

It excludes:

- `README.md`.
- `.gitignore` and `.gitattributes` (project-owned seeds).
- `docs/`.
- `_control/`.
- Project-generated state and records.

If any additional file is framework-managed, it must be explicitly included in the build's managed-file specification and tests.

## 7.4 Hash normalization and Windows line endings

The framework must not report false drift because Git converted LF to CRLF.

Use both protections:

1. Ship `.gitattributes` with explicit `eol=lf` rules for managed runtime/configuration/documentation text (`*.md`, `*.py`, `*.json`, `*.jsonl`, `*.toml`, `*.yaml`, `*.yml`, `*.txt`, `*.csv`, `*.xml`, `*.svg`, and root launcher/instruction files). Mark known binary formats (images, PDFs and archives) as binary or `-text` so Git never rewrites their bytes.
2. Hash managed text files after canonicalizing CRLF and CR to LF. Hash binary files as raw bytes.

The manifest must identify the hash mode for each file or use a deterministic extension/content classification documented in the schema. Do not silently normalize arbitrary binary data.

A regression test must:

- Build or create a disposable workspace.
- Initialize a Git repository.
- Configure `core.autocrlf=true`.
- Add and commit the workspace.
- Clone or check out the workspace under that configuration.
- Run `bp.py check --strict`.
- Confirm no false framework-drift errors occur.

The `.gitattributes` file is project-owned, so the framework should also check that required LF rules are present. If the owner deliberately removes them, report the missing policy. Normalized text hashes remain a second line of defence.

## 7.5 Manifest mismatch behavior and limitations

- Normal `check`: warn when a framework-managed file is missing, changed or unexpected relative to the manifest.
- `check --strict`: treat framework drift as an error.
- Malformed manifest or unsupported schema: error.
- `new`: refuse a package with an invalid manifest or a managed-file mismatch.

This manifest detects accidental drift, not malicious tampering. An agent able to edit both a file and its manifest can update both. It is not a trusted signature, code-integrity boundary or sandbox. External signatures may be considered in a later release-security project, but are not part of v3.0.0.

## 8.3 Workspace and source discovery

Workspace discovery walks upward from the current working directory until it finds a valid `_control/WORKSPACE.json` or reaches the filesystem root. The nearest valid workspace marker is selected.

Source discovery walks upward for `framework-dev/SOURCE-MANIFEST.json`. When the launcher runs from within the source repository—including from `starter/`—source mode is the correct result. `starter/_control/WORKSPACE.json.template` is a seed file only and must never select workspace mode.

Mode selection rules:

1. Inspect the current directory and ancestors for valid live markers, never template markers.
2. If exactly one recognized source marker is found and no live workspace marker is found, select source mode, including from `starter/` and other source subdirectories.
3. If exactly one recognized workspace marker is found and no source marker is found, select workspace mode.
4. If both source and workspace markers are found on the same ancestry chain, or multiple competing roots make the context ambiguous, stop with a diagnostic rather than guess. The supported `new` command prevents this state by refusing destinations inside the source repository.
5. `new` must refuse any destination whose resolved path is inside the source repository root. This prevents generated workspaces from polluting the source tree and avoids source Git-root instruction files affecting the evaluation/override scan.

The source marker is a source-repository identity marker, not a workspace marker. The starter must contain only `WORKSPACE.json.template`, never a live `WORKSPACE.json` until `new` materializes it. Add a regression that invokes the single source-root `bp.py` with `cwd=starter/` and asserts source mode is selected, workspace mode is not selected, and no workspace is created as a discovery side effect.

## 8.4 Path safety

The resolver must reject:

- Absolute paths where only workspace-relative paths are expected.
- `..` traversal in project-controlled paths.
- Symlinks that resolve outside the workspace for writes or protected reads.
- Unexpected path types (for example, a file where a directory is required).
- Invalid marker parents or inconsistent roots.
- Windows drive/UNC escape forms where a relative path is required.

Containment checks must resolve the path and compare it with the canonical workspace root. Do not rely only on string prefix comparison.

For symlink races, resolve/check as close as possible to the operation; do not use validated untrusted paths after a potentially changing symlink target without rechecking.

## 8.5 Project name, destination and path length

The suggested workspace folder name is `<ProjectName>-Blueprint`; it is a default convention, not a constraint. `--destination` may specify any safe destination. The project display name and destination basename are separate values.

Validate project names for Windows safety even when the source environment is Linux:

- Reject empty names and control characters.
- Reject `< > : " / \ | ? *`.
- Reject trailing spaces and periods.
- Reject `.` and `..`.
- Reject reserved Windows device names (including extensions and case variants).
- Apply a documented length limit.
- Preserve legitimate Unicode names.

The final destination path must not already exist. An existing empty directory is refused as well as a non-empty destination; this strict rule makes the cross-platform final rename unambiguous. The diagnostic must explain that the caller should choose a new destination path. Creation must not delete, merge, overwrite or modify existing content. If the suggested project slug becomes empty or invalid after normalization, `new` must require an explicit safe `--destination` rather than invent a fallback name.

`new` must refuse any destination whose resolved path is inside the framework source repository, including `starter/`, `dist/` and `framework-dev/`. This rule applies even when the destination path does not yet exist.

`new` must perform a path-length preflight. On Windows, calculate the destination root length plus the longest relative path required by the starter and catalog's expected document paths. Use a conservative default ceiling of 240 characters for anticipated generated paths, report the longest path and refuse creation when the budget is exceeded. The ceiling and rationale must be documented and tested. Do not assume long-path support is enabled.

Before packaging and creation, normalize each archive/workspace path to a canonical Unicode normalization form (NFC) and compare case-folded path keys. Reject collisions such as `README.md` versus `readme.md`, including collisions in parent directory components. This check is performed on every platform so a package accepted on a case-sensitive filesystem cannot fail or overwrite files on a case-insensitive filesystem.

# 9. Semantic-file discovery, document identity and assets

## 9.1 Document identity

Document identity remains based on:

- Stable document ID.
- Canonical document path relative to `docs/`.
- Existing approval-bearing content and metadata inputs.

A document's canonical path is stored without the `docs/` prefix, for example:

`04-architecture/system-context.md`

Moving the registry and framework directories must not add `_control/` or `_framework/` to document paths. Do not change the approval fingerprint algorithm or its normalized inputs in v3.0.0.

## 9.2 Semantic sources

The current implementation has literal filename exclusions. Replace those with explicit source-role classification.

Core classes:

- `catalog_document`: canonical project document under `docs/`.
- `project_context`: root README and other explicitly declared project context.
- `project_register`: decisions, assumptions, questions, risks and glossary registers.
- `agent_instruction`: AGENTS and PROJECT-RULES; instructions, not product requirements.
- `framework_reference`: `_framework/`; excluded from project semantic content.
- `operational_state`: STATE, MANIFEST, INDEX, approvals and logs; used for continuity/governance, not silently treated as requirements.
- `supporting_asset`: non-Markdown files under `docs/_assets/`.

The role definitions and default semantic-source classification are stored in hash-tracked `_framework/defaults/workspace-defaults.json`. `project_semantic_files` must consume that framework-owned classification and manifest/catalog metadata, not a list of magic filenames or arbitrary path values in `WORKSPACE.json`. A later schema may support narrowly scoped project extensions, but v3.0.0 does not expose a general path or semantic-source override surface.

Root `README.md` is project-owned context. It may be consulted for orientation, but a specific catalog-backed document remains authoritative for detailed project requirements or decisions.

## 9.3 Asset rules

Allowed asset types include images, PDFs, exported diagrams, machine-readable specifications and other explicitly supported attachments.

`docs/_assets/specs/` is the home for OpenAPI, JSON Schema, AsyncAPI, GraphQL SDL, Protobuf and similar machine-readable specifications.

Markdown files under `_assets/` are not exempt from orphan checks. The warning must say, for example:

> Markdown files are not treated as assets. Move this note into a catalog-backed document or `docs/99-appendix/`, then link it from the owning document.

Existing deliberate exceptions such as `docs/README.md`, the ADR directory and `99-appendix/` must be explicit and covered by tests.

Documents may reference assets using workspace-relative or document-relative links according to one documented convention. The checker must validate local references exist and remain within the workspace. It may validate the shape of supported specifications when an available local parser is deliberately added, but v3.0.0 must not claim semantic validation that it does not perform.

# 10. `bp.py` launcher and command contract

## 10.1 One launcher, two modes

The same thin `bp.py` launcher is used in the source repository and in generated workspaces. It detects context and dispatches to the corresponding implementation.

### Source mode

Detected by `framework-dev/SOURCE-MANIFEST.json` and the expected source tree.

Commands:

- `bp.py --version` — source version from `VERSION`.
- `bp.py verify` — source integrity, tests and build prerequisites.
- `bp.py build` — assemble starter staging tree, validate, generate the framework manifest and package the starter.
- `bp.py new` — locate `dist/project-blueprint-workspace-<VERSION>.zip` (or use `--package PATH`), verify and instantiate the built starter package. `new` never calls `build` implicitly.

Source-only implementations live under `src/blueprint_framework/`: `source_cli.py` dispatches source commands, `build.py` implements `build`, and `package.py` implements `new`/package verification. These source-only implementations are not copied into the starter or workspace. The source launcher locates the already-built package at `dist/project-blueprint-workspace-<VERSION>.zip` by default; `new --package PATH` permits an explicit package. If the package is missing, `new` reports that `build` must be run and does not build implicitly.

### Workspace mode

Detected by `_control/WORKSPACE.json`.

Commands include the existing workspace operations, adapted to the new paths:

- `--version`.
- `check [--strict] [--readiness] [--gate N]`.
- `status [--write]`.
- `index [--check]`.
- `scaffold`.
- `set-status`.
- `approve`.
- `maturity`.
- `applicability`.
- `profile`.
- `impact`.
- `graph`.
- `session`.

The exact help output and arguments must be generated from the actual CLI and used by documentation drift tests.

Workspace mode must not expose `build` or `new` as project commands. Source mode must not run workspace mutations against the source repository.

## 10.2 Launcher design

`bp.py` should remain thin. It performs only:

1. Context discovery.
2. Minimal argument dispatch.
3. Loading the correct implementation.
4. Converting controlled errors into useful exit codes/messages.

It must not duplicate business logic or contain separate copies of the workspace command implementation.

Before importing source/workspace implementation modules or dispatching commands, the launcher checks `sys.version_info`. If Python is below 3.11, it prints the detected version, a clear minimum-version error and platform-appropriate interpreter-selection examples, then exits with a dedicated unsupported-interpreter code. This guard applies in source and workspace mode. Because the guard must run under an unsupported interpreter, the tiny top-level launcher itself must remain parseable using Python 3.8 grammar and import only standard-library modules before the check; it must not use newer syntax or import implementation modules first. Add a grammar-compatibility test (for example, parsing the launcher with the oldest grammar target supported by the test runtime) in addition to the runtime guard test.

Source mode imports source-only commands. Workspace mode loads `_framework/tools/blueprint.py`. Source-only modules are not shipped. Documentation must not assume the command `python` resolves to the desired interpreter.

The exact implementation mechanism (ordinary import, importlib loading or a small package bootstrap) is an implementation choice, but it must be deterministic, testable and independent of the current working directory once a valid root is discovered.

## 10.3 Source marker and starter marker

- Source marker: `framework-dev/SOURCE-MANIFEST.json`.
- Workspace marker: `_control/WORKSPACE.json`.
- Starter seed: `starter/_control/WORKSPACE.json.template`.

When `bp.py` is executed from inside `starter/` within the source repository, it must discover the source marker in an ancestor and select source mode. It must not select workspace mode merely because the starter contains a directory named `_control/`. The `.template` file is never a live marker.

A regression test must invoke the actual root launcher with `cwd=starter/` and assert that source mode is selected and workspace mode is not selected. The test must also prove that no `new` destination is created as a side effect of mode discovery.

## 10.4 `new` command

Suggested command, run from the framework source repository:

```text
python bp.py new --name "Example Project" --destination "C:\PBF\Workspaces\Example Project-Blueprint"
```

If `--destination` is omitted, derive the default as a sibling of the source repository: `<source-root-parent>/<project-slug>-Blueprint`. The slug is produced by Unicode NFC normalization, trimming, replacing each run of whitespace with `-`, and preserving other valid Unicode letters/numbers plus safe `-` and `_` characters; project-name validation rejects filesystem-unsafe characters before slugging. If the derived destination already exists, refuse and require an explicit new destination. The default is a convenience, not a restriction: `--destination` may point elsewhere, subject to all safety rules. The project display name and destination basename are independent.

Additional option:

- `--package PATH` selects a specific already-built workspace starter archive. Without it, source mode uses `dist/project-blueprint-workspace-<VERSION>.zip`.

If the artifact is absent, report that `build` must be run or a package path supplied. `new` must not silently invoke `build`.

### Destination and source-tree rules

- Destination parent directories may be created as needed, with created parent directories recorded for diagnostics; failure cleanup must not delete pre-existing parent directories.
- The final destination path itself must not already exist. An existing empty directory is also refused with a clear message; the user can provide a new path. A non-empty destination is always refused.
- The resolved destination must not be inside the framework source repository, including `dist/`, `starter/` or `framework-dev/`.
- The destination must not be the source repository root or any protected source subtree.
- Validate project name, destination path length and case-insensitive path collisions before final placement.
- `new` does **not** run `git init`. It prints optional Git initialization commands after successful creation; repository initialization remains an explicit owner action.

### Creation algorithm

1. Validate source mode and locate the source root.
2. Resolve source `VERSION` and the expected already-built package.
3. Validate archive integrity, safe member paths, duplicate paths and case-fold/Unicode-normalization collisions before extraction.
4. Validate the project name, resolved destination, path-length budget and source-tree exclusion.
5. Require the final destination path not to exist. Create any missing destination parent directories only as necessary and track which ones this invocation created.
6. Create a uniquely named temporary staging directory as a sibling of the final destination under the same parent/filesystem. Do not stage in the global temporary directory or another volume.
7. Extract the starter package into the sibling staging directory while rejecting absolute paths, traversal, symlink entries and unsafe archive members.
8. Verify `_framework/FRAMEWORK-MANIFEST.json`, every managed-file hash, required files, supported workspace schema/layout versions, and the root `AGENTS.md` character budget.
9. Materialize project-owned `README.md` and `_control/WORKSPACE.json` values. Do not edit or substitute `AGENTS.md` or `bp.py`.
10. Rename `starter/_control/WORKSPACE.json.template` to the live `_control/WORKSPACE.json` inside staging.
11. Write every generated text file as UTF-8 without BOM and LF line endings. Do not depend on host locale or platform defaults.
12. Initialize project-owned registers and state with accurate empty/initial values. Do not invent decisions, approvals, history or session records. Create required files; optional empty directories may be omitted.
13. Verify that no project documents were bulk-scaffolded. Run strict workspace validation, index verification, framework-manifest verification, local-link checks and generated-file encoding checks in staging.
14. Recheck that the final destination is still absent immediately before promotion, then use a same-filesystem directory rename from the sibling staging directory. Clean up only the staging directory and newly created empty parent directories that are provably owned by this invocation if creation fails; never remove pre-existing paths or source content. Portable standard-library Python does not expose a cross-platform atomic no-replace directory rename on every POSIX host. A small race remains if an unrelated process creates the destination between the final check and rename; document this limitation rather than adding platform-specific `ctypes`/`renameat2` code or refusing otherwise safe single-user operation.
15. Print the destination, next steps, interpreter guidance, validation commands, agent-start instructions, first-prompt location and optional Git initialization commands. Do not execute `git init`.

`new` must not scaffold all catalog-backed project documents. It does **not** run `git init`; repository initialization is an explicit owner action. Successful output may print optional `git init` / first-commit instructions.

## 10.5 `build` command and release artifacts

`bp.py build` is the core workspace-starter build. It verifies the maintained source and runs the active tests by default, assembles a project-neutral starter ZIP, extracts and validates the candidate package, and only then publishes the generated starter artifact. It does not compile the full Agent-First Release.

The developer repository's `tools/release/build_release.py` is the authoritative full release compiler. It reads the root `VERSION`, runs maintained verification and tests, calls the existing workspace build, assembles the curated bootstrap runtime, creates the nested agent package and outer Agent-First Release ZIP, generates manifests/checksums and verifies the exact final package with a disposable end-to-end bootstrap. The normal release build produces exactly one product deliverable.

Generated release artifacts are written under `dist/`, which is ignored by Git. Existing final artifacts are not replaced unless the maintainer explicitly supplies the documented force option; failed candidate builds must not damage an earlier successful output.

# 14. Framework build, creation and integrity lifecycle

## 14.1 Build-time manifest generation

The `build` command assembles the starter in a temporary staging directory. Only after all managed files have been copied and normalized does it generate `FRAMEWORK-MANIFEST.json`.

It reads the source-root `VERSION`; it does not invent or derive a version from `WORKSPACE.json`.

The generated manifest is deterministic:

- Stable sorted file list.
- Stable workspace-root-relative POSIX paths.
- SHA-256.
- LF-normalized text hashes.
- Raw binary hashes.
- No timestamps in hash identity unless a future schema explicitly requires them.
- Manifest excludes itself.

## 14.2 `new` verification

`new` verifies the built archive against the included manifest before copying it into the destination. It does not recalculate the baseline. A malformed, unsupported or mismatched package is refused.

## 14.3 Runtime drift checking

`check` reports managed-file drift as a warning. `check --strict` promotes it to an error. This is useful for accidental edits, incomplete updates or line-ending mishandling.

The framework must tell the owner which managed file differs and its expected/actual normalized hash state. It must not automatically rewrite the file or manifest during `check`.

## 14.4 Source `verify` environment record

`verify` must report, at minimum:

- `sys.executable` or a safe abbreviated interpreter path.
- Python implementation and full version string.
- OS/platform identifier and release.
- Machine architecture.
- Framework source version.
- Test command/result summary when tests are requested or run by `verify`.

The command must not claim the complete supported Python/platform matrix was executed. It prints a concise environment/result block containing the actual interpreter implementation/version, OS/platform and architecture used for that invocation. It does not create a separate structured environment-evidence file in v3.0.0; that automation belongs with the future CI/release-evidence workflow. Release notes must state only environments actually used in ordinary development and release verification, using the wording: **“Requires Python 3.11+; verified on [actual environment(s)].”** No dedicated manual 3.11–3.15 matrix is required for v3.0.0.

## 14.5 No update/refresh command in v3.0.0

There is no general `refresh` or upgrade command. A new workspace is created from the current starter package; the owner is responsible for deciding how any existing workspace is handled.

A general framework update/merge mechanism is future work and should only be designed when a real, retained project workspace needs it. The manifest establishes the future foundation; it is not a reason to build an update engine prematurely.

## 14.6 Source verification scopes

Source verification has two explicit scopes that share the same runtime invariants but serve different trust boundaries:

- **Bootstrap scope:** `bp.py verify --scope bootstrap` validates the source marker, version, launcher, workspace runtime, framework defaults, starter inputs and source modules needed to execute `bp.py new`. It does not require developer documentation, maintainer tests, historical records or a Git repository.
- **Maintainer scope:** `bp.py verify` validates the maintained source tree, normative developer documentation, active tests/tooling files, text encoding, Python syntax, path/symlink hygiene and release assets. `bp.py verify --tests` additionally executes every maintained test module in an independent interpreter process.

The bootstrap runtime archive is generated from the verified runtime inputs, not by selecting files from the old historical source archive. The full developer repository remains the authoritative source for future changes.

It does not contain the full maintainer source or maintainer test suite.

The full maintainer source and active tests remain in the developer repository. Raw local build logs remain in ignored `dist/` output, not in the user-facing release. Shipped evidence is a concise summary generated from the current build and records verification steps, exit statuses, test counts, artifact hashes and known limitations without publishing host-specific environment fingerprints.

# 21. Explicitly deferred work

The following are outside the v3.0.0 stable scope unless the owner approves a scope change:

- A CI workflow or complete automated OS/Python-version matrix.
- A general framework update/merge engine or workspace upgrade mechanism.
- v2.x workspace-layout compatibility or migration.
- A general in-place workspace upgrade or refresh mechanism.
- Template override resolution and `_control/overrides/templates/`.
- TRACE001 as an approval-blocking lint rule.
- Automated semantic traceability proof.
- Signed release manifests or tamper-resistant publisher trust anchors.
- Universal certification across AI harnesses.
- Application source-code integration.
- Bulk scaffolding or code-generation features.

The framework integrity manifest, maintained tests, workspace starter build and full Agent-First release compiler are in scope. The absence of CI does not excuse tests from being deterministic, self-contained and locally runnable.

# 22. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Hidden old path references remain | Commands fail in less common operations | Central `WorkspacePaths`; source search; integration tests across CLI operations. |
| Agent does not load `AGENTS.md` automatically | Required framework guidance may be missed | Require explicit bootstrap unless automatic loading is independently verified. |
| Agent environment lacks persistent filesystem or terminal access | Setup cannot complete or workspace may be ephemeral | Check actual capabilities and stop rather than claiming success. |
| Agent assumes a container path is a host path | Workspace is created in an unintended or ephemeral location | Explain path visibility and obtain approval for the exact persistent destination. |
| Agent begins P0 after setup without approval | Owner loses control over the discovery start | Treat setup completion and P0 as separate stages with explicit confirmation. |
| Framework update overwrites project-specific rules | Owner preferences are lost | `AGENTS.md` is framework-managed; `PROJECT-RULES.md` is project-owned and excluded from the framework manifest. |
| Manifest hashes differ due to CRLF | False strict-validation failures | `.gitattributes` LF policy plus normalized text hashing and Git `core.autocrlf=true` regression test. |
| Manifest treated as a security control | False confidence | State that in-workspace manifest detects drift but cannot prevent coordinated tampering. |
| Starter marker is mistaken for an active workspace | Source commands dispatch incorrectly | Use `WORKSPACE.json.template` and exact source/workspace marker tests. |
| Workspace package extraction is partial | Incomplete destination | Validate archive, stage safely, check the exact generated workspace and preserve partial output for inspection on failure. |
| Release and source inputs drift | Package is not reproducible | Build from authored `release-assets/`, generate manifests/checksums, and verify the exact final ZIP. |
| Release builder replaces valid output on failure | Prior release is lost | Build to temporary candidates and promote only after all gates; require `--force` for replacement. |
| Generic harness claims exceed evidence | Users rely on unsupported behavior | Limit claims to tested environments and label unknown behavior explicitly. |
| Premature TRACE001 yields false positives | Good requirements fail lint | Keep deferred until reliable entry structure and false-positive evidence justify it. |
| No CI is configured | Regression gate depends on local execution | Document exact maintainer commands and retain isolated deterministic test modules. |

# 23. Final architecture acceptance checklist

The following checklist records the accepted architecture baseline; implementation must not silently change these decisions:

### Workspace and ownership

- [ ] The canonical workspace root contains `README.md`, `AGENTS.md`, `bp.py`, `docs/`, `_framework/` and `_control/`; application source code is outside it.
- [ ] The developer source tree, authored release assets and generated outputs have clearly separated ownership and packaging boundaries.
- [ ] Framework-owned files, project-owned seeds/state, generated files and source-only files have one explicit owner and update rule.
- [ ] `AGENTS.md` is framework-managed, byte-identical from source starter to workspace, project-neutral, at most 14,000 characters and targeted at 12,000 or less; the static instruction-hygiene test passes.
- [ ] `_control/PROJECT-RULES.md`, README, PHASES, WORKSPACE configuration and Git hygiene files remain project-owned after creation.
- [ ] The core contract is agent-harness-neutral; no automatic context loading is assumed without evidence.

### Configuration, versions and paths

- [ ] Source `VERSION` is the sole release-version input; the build embeds it in `_framework/FRAMEWORK-MANIFEST.json`.
- [ ] `_control/WORKSPACE.json` contains workspace schema/layout versions and permitted project settings only; it has no framework version or arbitrary `paths` map.
- [ ] Static profile/bootstrap/catalog/index defaults and visible policy prose live in hash-tracked `_framework/defaults/` files; the documented v3 configuration owns only approved project-variable settings.
- [ ] One `WorkspacePaths` resolves every workspace runtime location, including catalog, templates, defaults, ADR, registries, state and `status-transitions.jsonl`; `SourcePaths` handles source-only paths.
- [ ] Layout version 1 uses `docs/04-architecture/adr/`; document-relative paths and the v2.3.3 golden fingerprint are unchanged.
- [ ] Required files/structural roots and optional/on-demand directories are explicitly defined; missing empty directories do not invalidate a workspace.

### Launcher, build and workspace creation

- [ ] Source and workspace distributions use the same thin, byte-identical `bp.py`; source-only implementation modules are not shipped.
- [ ] The starter contains only `WORKSPACE.json.template`; executing the launcher from `starter/` selects source mode and creates no workspace as a side effect.
- [ ] The launcher rejects Python below 3.11 before dispatch and remains parseable by the documented pre-3.11 grammar.
- [ ] `build` generates the manifest from source `VERSION`; `new` verifies it without regenerating it.
- [ ] The workspace archive contains root-relative members with no unexpected enclosing directory; unsafe paths, symlinks and case/Unicode collisions are rejected.
- [ ] `new` refuses source-tree and existing destinations, validates names/slugs/path length, stages beside the destination, and uses sibling staging plus same-filesystem rename after a final destination recheck; the residual race is documented.
- [ ] `new` writes UTF-8-without-BOM/LF text, does not run `git init`, prints optional Git instructions and does not bulk-scaffold catalog documents.
- [ ] Root README contains the quick start and first prompt; `docs/README.md` navigates documents and stakeholder registers.

### Agent, state and setup

- [ ] The Agent-First Release supports agent-assisted setup from one outer ZIP; the temporary bootstrap runtime and generated workspace remain separate.
- [ ] The agent explicitly reads the generated `AGENTS.md` and `_control/PROJECT-RULES.md`; actual file access, Python, terminal and persistent destination capability are established before setup.
- [ ] Native instruction discovery, context limits, truncation and security scanners are not assumed; any harness-specific claim is version-evidenced or clearly marked unverified.
- [ ] Setup completion and P0 discovery are separate stages; the agent waits for the owner's explicit confirmation before beginning P0.
- [ ] Setup provenance is recorded concisely in an existing initial project-control record, without creating unnecessary session/audit artifacts.
- [ ] State startup/checkpoint procedures preserve decisions, assumptions, questions, approvals, session history and generated-index consistency.

### Quality, tests and release

- [ ] Selected-profile audit fields and readiness statuses are implemented; readiness remains advisory and does not replace owner review.
- [ ] `TRACE001`, template overrides, legacy support, refresh/migration and CI remain deferred as specified.
- [ ] The 94 compatibility regression tests have one-to-one maintained v3 ports documented in the compact baseline fixture; no historical test archive is needed by source verification.
- [ ] Tests cover path/symlink safety, case and Unicode collisions, Windows names, UTF-8/LF, Git `core.autocrlf=true`, marker selection, manifest drift, fingerprint preservation and archive extraction.
- [ ] Internal links/anchors and CLI documentation match the shipped files and actual help output; no active old-layout commands or paths remain before release.
- [ ] `verify` reports only the interpreter/platform actually used; no unexecuted Python/OS matrix is claimed.
- [ ] The complete Agent-First Release ZIP passes fresh-extraction checksum/manifest verification and an end-to-end disposable workspace bootstrap before publication.
