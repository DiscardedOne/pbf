## 1. Release purpose

This release provides a simpler user-facing distribution for the stable PBF v{{PBF_VERSION}} framework. The framework runtime and accepted workspace architecture remain at version {{PBF_VERSION}} / revision 1.3.4. The distribution redesign changes packaging and onboarding: an ordinary user downloads one outer ZIP and provides it to a capable agent, which verifies the package, confirms a persistent destination with the owner, creates a workspace using the existing CLI and asks separately before beginning P0.

PBF remains a reusable methodology and supporting tooling. It is not an AI model, agent runtime, hosted platform, autonomous development environment or operating-system sandbox.

## 2. Release production model

The developer repository is the authoritative input. Its standard build produces exactly one product artifact:

```text
dist/PBF-v<VERSION>-Agent-First-Release.zip
```

The build process verifies the maintained source and tests, invokes `bp.py build` to create the workspace starter, assembles a curated bootstrap runtime, creates the nested agent package, creates the outer release and verifies the exact final ZIP through extraction and disposable end-to-end setup.

## 3. Package contents

The outer Agent-First Release contains:

- `README.md` and `QUICKSTART.md`.
- `RELEASE-MANIFEST.json` and `SHA256SUMS.txt`.
- `docs/README.md` and six consolidated Markdown references directly under `docs/`.
- Concise current-build evidence under `release-evidence/`.
- One nested agent package at `agent-package/PBF-Agent-Package-v<VERSION>.zip`.

The nested agent package contains:

- `AGENT-OPERATING-INSTRUCTIONS.md` and `AGENT-STARTUP-PROMPT.md`.
- `PACKAGE-MANIFEST.json` and `SHA256SUMS.txt`.
- A curated `bootstrap-runtime` ZIP containing only the verified files needed to run `bp.py new` and verify the runtime.
- The generated project-neutral workspace starter ZIP.
- `tools/bootstrap.py`.

The nested package does not contain the full maintainer source repository or developer regression suite. The complete source and test suite remain in the developer repository; local build logs are not included in the user-facing package.

## 4. Verification context

The developer repository maintains the current source test suite and bootstrap-tool tests. The exact test-method inventory, commands, verification context and outcomes for each published ZIP are generated into `release-evidence/BUILD-VERIFICATION.md`; do not carry test counts forward from a different source tree or build.

The current developer tree retains the 94 behavior regression tests from the compatibility baseline, with one-to-one port identities and equivalence notes in `framework-dev/tests/fixtures/regression-baseline.json`. The current suite focuses on source-scope and bootstrap validation. The maintained inventory currently contains 235 framework/developer tests and 19 bootstrap tests (254 total methods). The actual pass count for a particular release must come from that build's generated verification evidence, not from this static document.

## 5. Build evidence

`release-evidence/BUILD-VERIFICATION.md` is generated by the release compiler for the exact artifact. It records:

- framework version and workspace architecture revision;
- confirmation that the build interpreter met the declared Python 3.11+ minimum;
- exact verification/build commands and their exit codes;
- maintained test module/method counts and actual result;
- workspace starter file count and SHA-256;
- bootstrap-runtime, nested-package and outer-release SHA-256 values;
- archive CRC/manifest/checksum results;
- end-to-end disposable workspace creation and validation results;
- limitations and checks not performed.

No raw source build logs or personal development-environment records are included in the ordinary release. If an execution step fails or is not run, evidence must say so; a planned command is not a test result.

## 6. Compatibility and non-claims

- **Python minimum:** CPython/Python 3.11 or newer is declared. A complete test matrix for every later Python minor version is not established merely by that declaration.
- **Native Windows:** not claimed unless a native Windows release build and workspace setup are separately verified.
- **AI harnesses:** the design is agent-harness-neutral, but no universal or cross-harness compatibility certification is claimed. Agent setup requires actual persistent filesystem access, write permissions, terminal execution and a Python 3.11+ interpreter in the environment that can access the destination.
- **Security boundary:** bootstrap checks and instructions are not an OS-level sandbox. Actual isolation is defined by the host and permissions.
- **Network/software installation:** setup does not install software or make network calls.
- **Git:** workspace creation does not initialize Git.
- **Integrity:** compare the downloaded outer ZIP SHA-256 with the value in the official GitHub Release description. This relies on trust in the PBF GitHub account/repository; it is not a detached digital signature.
- **Semantic correctness:** deterministic checks do not prove the completeness or correctness of project requirements, architecture or owner decisions.
- **CI:** no CI workflow is configured unless the generated evidence explicitly reports a later configured pipeline.
